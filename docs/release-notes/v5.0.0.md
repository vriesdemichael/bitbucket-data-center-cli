### Upgrading to v5: Automation & Scripting Checklist

If you consume `bb` inside CI/CD pipelines, shell scripts, or AI agent toolchains, review this checklist before upgrading:

1. **`bb pr checks` gates on CI the way `gh pr checks` does ([ADR-091](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/091-a-command-may-report-the-state-it-read-through-its-exit-status/), [#646](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/646)):**
   * Without `--json`, `bb pr checks` and `bb pr build status` exit `1` when a build failed, and `8` when none failed and one is still in progress or has no result. They used to exit `0` whatever the builds said, so a gate written for `gh`, `bb pr checks 42 || exit 1`, let every pull request through.
   * A failed build wins over one still running, and a cancelled build counts as neither. The exit status covers every build, not only the `--limit` shown. When it is not `0`, a line on stderr says how many builds failed or are still running.
   * Exit `8` is new to `bb`. It is not an error kind, and only these two commands use it.
   * Under `--json` both commands still exit `0`, with each build's state in `data.statuses`, as `gh pr checks --json` does.
   * A script that runs either command for its output and relies on exit `0` adds `|| true`, or passes `--json`.
2. **`bb bulk` is gone, as the v4.1.0 notes announced ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/), [#608](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/608)):**
   * `bb bulk plan`, `bb bulk apply` and `bb bulk status` no longer exist, nor do `BB_BULK_STATUS_DIR` and the bulk policy, plan and apply-status schemas.
   * Set permissions, webhooks, default tasks and branch restrictions once on the project, with `bb project permissions`, `bb project webhook`, `bb project default-task` and `bb project branch-restriction`. Bitbucket applies them to every repository in the project.
   * For a setting Bitbucket keeps per repository, loop over `bb repo list --project PROJ --json` and run the `bb repo settings` command for each, previewing with `--dry-run`.
   * The bb-bulk agent skill is gone too, so `bb ai skill install bulk` exits `2`. Delete any copy an earlier bb installed, in `.agents/skills/bb-bulk` or `.claude/skills/bb-bulk`, in a project or in your home directory. `bb doctor` names every copy it finds.
3. **`--dry-run` answers with a verdict, in its own member ([ADR-096](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/096-the-flags-choose-the-member-and-dry-run-answers-with-a-verdict/), [#616](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/616)):**
   * Under `--json`, a dry run answers in `preview` rather than `data`: a `tier`, one effect per change with its `action`, `target`, `outcome` (`would-apply`, `no-op` or `would-fail`) and `reasons`, and the `error` the real run would fail with. `dryRun`, `planningMode`, `capability`, `summary`, and per item `intent`, `predictedAction`, `supported`, `confidence`, `requiredState` and `blockingReasons` are gone; a script reading `summary` reads `effects` instead. `bb --json pr merge 42 --dry-run`, for a pull request that is already merged:

     <!-- docs-lint: envelope-shape -->
     ```json
     {
       "preview": {
         "tier": "preconditions-checked",
         "effects": [
           {
             "action": "update",
             "target": { "id": "42", "repository": "PROJ/app" },
             "outcome": "would-fail",
             "reasons": ["pull request is already merged"]
           }
         ],
         "error": { "kind": "conflict", "message": "pull request is already merged", "exitCode": 5 }
       },
       "meta": { "command": "pr merge", "bbVersion": "..." }
     }
     ```
   * A command that only reads still runs, and its data is in `preview.data`. A failure the check runs into, such as invalid arguments or a missing pull request, is `preview.error` rather than a top-level `error`, which under `--dry-run` now means only that no verdict was reached: `10` Bitbucket did not answer, `12` interrupted, `1` a bug in bb.
   * Without `--json`, a dry run that finds the run would fail exits with the code the real run would, so `bb pr merge 42 --dry-run && bb pr merge 42` stops at the check. It used to exit `0`. Under `--json` or `--yaml` a verdict exits `0`, with the verdict in the document.
   * The text output names each change and why it would or would not go through, in place of the `intent=... action=...` lines.
   * `bb ai mcp serve` no longer takes `--dry-run`.
   * There is no warning period: one document cannot carry the old preview beside the new one.
4. **`--describe` describes the whole document, for a run and for a dry run ([ADR-097](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/097-describe-describes-a-commands-output-in-every-mode/), [#616](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/616)):**
   * Under `--json` it answers in `description` rather than `data`. `run.outputSchema` is the JSON Schema of the whole document a run writes, meta and the error included, and `dryRun.outputSchema` the one `--dry-run` writes, beside `dryRun.behaviour` and `dryRun.tier`. `described` is gone, `command` is `meta.command` and `reason` is `run.reason`. A script reading `schema` reads `run.outputSchema.oneOf[0].properties.data`, or better, validates the whole document against `run.outputSchema`.
   * Without `--json` or `--yaml` it prints an outline of the fields for people, rather than the JSON Schema.
   * `bb <group> --describe` and `bb --describe` list their commands with what `--dry-run` does for each, rather than saying a group has nothing to describe. A path that names no command answers with `description.error`, exiting `0` under `--json`.
   * There is no warning period: one document cannot carry the old description beside the new one.
5. **The MCP server asks your permission in your MCP client, and offers every tool by default ([ADR-098](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/098-mcp-tools-that-decide-a-merge-ask-the-person/), [#620](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/620)):**
   * `bb ai mcp serve` moves to MCP's newer way of asking for permission, elicitation: the server asks, and your MCP client shows you the question. By default it offers every tool, as it did with `--yolo`, but a tool that merges, or decides what merges or gets released, asks you first. That covers merging, turning auto-merge on or off, approving or requesting changes, reporting a build status, creating a tag, and moving a pull request into or out of draft. Your client shows what the call will do, and it runs only once you accept. Before, the server hid most of these unless it started with `--yolo`, and then nobody was asked.
   * Locking the server down is now opt-in: with `--read-only` it offers only the tools that read. `--yolo` and `--allow-writes` do nothing, and warn.
   * You accept the pull request you were shown. If someone pushes to it before you accept, the merge or auto-merge is refused.
   * Those tools need a client that supports elicitation. One that does not gets error `-32021` for them, and nothing changes in Bitbucket.
   * For MCP clients and audit pipelines: every tool declares all four MCP hints and a title as the specification defines them, so a client that decides its own prompts from the hints may prompt for different tools. `openWorldHint` is false on every tool, and `update_pull_request` and `disable_auto_merge` are destructive. The audit record has `confirmation` (`accepted`, `declined`, `cancelled` or `unavailable`), and a call the confirmation stops is `status: denied`. `bb ai mcp tools` has `asks` (`always`, `never` or `when-setting-draft`) and takes `--read-only`. `bb ai mcp tools --json` for one tool:

     ```json
     {
       "name": "merge_pull_request",
       "description": "Merge a pull request. All required build checks must pass and all reviewers must have approved. Asks the person to confirm in the client before it runs.",
       "writes": true,
       "asks": "always",
       "safe": true,
       "exposure": "SAFE"
     }
     ```

### Deprecation

* **`bb update --json`: `scheduled`, `staged`, `paths.staged` and `paths.swapResult` are deprecated and are removed in v6.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/), [ADR-092](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/092-bb-update-installs-the-new-binary-itself-before-it-exits/)).**
  * `bb update` installs the new binary itself before it exits, on every operating system, so these fields are always false or empty. Read `applied` instead.
* **`bb ai mcp serve --yolo` and `--allow-writes`, `bb ai mcp tools --safe-only`, and the `safe` and `exposure` fields of `bb ai mcp tools --json` are deprecated and are removed in v6.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/), [ADR-098](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/098-mcp-tools-that-decide-a-merge-ask-the-person/)).**
  * Every tool is exposed without `--yolo`, so the flags do nothing, `--safe-only` lists every tool, `safe` is always true and `exposure` always `SAFE`. Pass `--read-only` for a server that only reads, and read `asks` and `writes` instead of the fields.
