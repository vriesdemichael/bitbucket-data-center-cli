### Upgrading to v5: Automation & Scripting Checklist

If you consume `bb` inside CI/CD pipelines, shell scripts, or AI agent toolchains, review this checklist before upgrading:

1. **`bb pr checks` gates on CI the way `gh pr checks` does ([ADR-091](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/091-a-command-may-report-the-state-it-read-through-its-exit-status/), [#646](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/646)):**
   * Without `--json`, `bb pr checks` and `bb pr build status` exit `1` when a build failed, and `8` when none failed and one is still in progress or has no result. They used to exit `0` whatever the builds said, so a gate written for `gh`, `bb pr checks 42 || exit 1`, let every pull request through.
   * A failed build wins over one still running, and a cancelled build counts as neither. The exit status covers every build, not only the `--limit` shown. When it is not `0`, a line on stderr says how many builds failed or are still running.
   * Exit `8` is new to `bb`. It is not an error kind, and only these two commands use it.
   * Under `--json` both commands still exit `0`, with each build's state in `data.statuses`, as `gh pr checks --json` does.
   * A script that runs either command for its output and relies on exit `0` adds `|| true`, or passes `--json`.
2. **`bb bulk` is gone, as the v4.1.0 notes announced ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/), [#608](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/608)):**
   * `bb bulk plan`, `bb bulk apply` and `bb bulk status` no longer exist, nor do `BB_BULK_STATUS_DIR` and the bulk policy, plan and apply-status schemas.
   * Set permissions, webhooks, default tasks and branch restrictions once on the project, with `bb project permissions`, `bb project webhook`, `bb project default-task` and `bb project branch-restriction`. Bitbucket applies them to every repository in the project.
   * For a setting Bitbucket keeps per repository, loop over `bb repo list --project PROJ --json` and run the `bb repo settings` command for each, previewing with `--dry-run`.
   * The bb-bulk agent skill is gone too, so `bb ai skill install bulk` exits `2`. Delete any copy an earlier bb installed, in `.agents/skills/bb-bulk` or `.claude/skills/bb-bulk`, in a project or in your home directory. `bb doctor` names every copy it finds.
3. **`--dry-run` answers with a verdict, in its own member ([ADR-096](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/096-the-flags-choose-the-member-and-dry-run-answers-with-a-verdict/), [#616](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/616)):**
   * Under `--json`, a dry run answers in `preview` rather than `data`: a `tier`, one effect per change with its `action`, `target`, `outcome` (`would-apply`, `no-op` or `would-fail`) and `reasons`, and the `error` the real run would fail with. `dryRun`, `planningMode`, `capability`, `summary`, and per item `intent`, `predictedAction`, `supported`, `confidence`, `requiredState` and `blockingReasons` are gone; a script reading `summary` reads `effects` instead. `bb --json pr merge 42 --dry-run`, for a pull request that is already merged:

     <!-- docs-lint: envelope-shape -->
     ```json
     {
       "preview": {
         "tier": "preconditions-checked",
         "effects": [
           {
             "action": "update",
             "target": { "id": "42", "repository": "PROJ/app" },
             "outcome": "would-fail",
             "reasons": ["pull request is already merged"]
           }
         ],
         "error": { "kind": "conflict", "message": "pull request is already merged", "exitCode": 5 }
       },
       "meta": { "command": "pr merge", "bbVersion": "..." }
     }
     ```
   * A command that only reads still runs, and its data is in `preview.data`. A failure the check runs into, such as invalid arguments or a missing pull request, is `preview.error` rather than a top-level `error`, which under `--dry-run` now means only that no verdict was reached: `10` Bitbucket did not answer, `12` interrupted, `1` a bug in bb.
   * Without `--json`, a dry run that finds the run would fail exits with the code the real run would, so `bb pr merge 42 --dry-run && bb pr merge 42` stops at the check. It used to exit `0`. Under `--json` or `--yaml` a verdict exits `0`, with the verdict in the document.
   * The text output names each change and why it would or would not go through, in place of the `intent=... action=...` lines.
   * `bb ai mcp serve` no longer takes `--dry-run`.
   * There is no warning period: one document cannot carry the old preview beside the new one.
4. **`--describe` describes the whole document, for a run and for a dry run ([ADR-097](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/097-describe-describes-a-commands-output-in-every-mode/), [#616](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/616)):**
   * Under `--json` it answers in `description` rather than `data`. `run.outputSchema` is the JSON Schema of the whole document a run writes, meta and the error included, and `dryRun.outputSchema` the one `--dry-run` writes, beside `dryRun.behaviour` and `dryRun.tier`. `described` is gone, `command` is `meta.command` and `reason` is `run.reason`. A script reading `schema` reads `run.outputSchema.oneOf[0].properties.data`, or better, validates the whole document against `run.outputSchema`.
   * Without `--json` or `--yaml` it prints an outline of the fields for people, rather than the JSON Schema.
   * `bb <group> --describe` and `bb --describe` list their commands with what `--dry-run` does for each, rather than saying a group has nothing to describe. A path that names no command answers with `description.error`, exiting `0` under `--json`.
   * There is no warning period: one document cannot carry the old description beside the new one.
5. **The MCP server asks your permission in your MCP client, and offers every tool by default ([ADR-098](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/098-mcp-tools-that-decide-a-merge-ask-the-person/), [#620](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/620)):**
   * `bb ai mcp serve` moves to MCP's newer way of asking for permission, elicitation: the server asks, and your MCP client shows you the question. By default it offers every tool, as it did with `--yolo`, but a tool that merges, or decides what merges or gets released, asks you first. That covers merging, turning auto-merge on or off, approving or requesting changes, reporting a build status, creating a tag, and moving a pull request into or out of draft. Your client shows what the call will do, and it runs only once you accept. Before, the server hid most of these unless it started with `--yolo`, and then nobody was asked.
   * Locking the server down is now opt-in: with `--read-only` it offers only the tools that read. `--yolo` and `--allow-writes` do nothing, and warn.
   * You accept the pull request you were shown. If someone pushes to it before you accept, the merge or auto-merge is refused.
   * Those tools need a client that supports elicitation. One that does not gets error `-32021` for them, and nothing changes in Bitbucket.
   * For MCP clients and audit pipelines: every tool declares all four MCP hints and a title as the specification defines them, so a client that decides its own prompts from the hints may prompt for different tools. `openWorldHint` is false on every tool, and `update_pull_request` and `disable_auto_merge` are destructive. The audit record has `confirmation` (`accepted`, `declined`, `cancelled` or `unavailable`), and a call the confirmation stops is `status: denied`. `bb ai mcp tools` has `asks` (`always`, `never` or `when-setting-draft`) and takes `--read-only`. `bb ai mcp tools --json` for one tool:

     ```json
     {
       "name": "merge_pull_request",
       "description": "Merge a pull request. All required build checks must pass and all reviewers must have approved. Asks the person to confirm in the client before it runs.",
       "writes": true,
       "asks": "always",
       "safe": true,
       "exposure": "SAFE"
     }
     ```

6. **Put a pull request, a diff or a file in front of the AI yourself ([ADR-099](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/099-mcp-resources-prompts-and-completions/), [#685](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/685)):**

   Until now the AI only saw what it went and fetched through bb's tools, so you had to hope it found the right pull request or file. Now you can hand it Bitbucket content yourself, the way you attach a file to a message: the pull request you are reviewing, its diff or its open comments, a file on any branch, tag or commit, or a single commit. Your MCP client helps you find it, suggesting projects, repositories, pull requests, paths and branches as you type, and it lists your own open pull requests and the ones waiting on your review, so the one you want is usually a click away.

   In VS Code, for example, choose Add Context > MCP Resources, pick the diff of pull request 42 in PAYMENTS/ledger, and ask what could break. Or type `/bitbucket.review_pull_request` to attach a pull request with its diff and open comments and ask for a review in one step. It works the same in any MCP client, including chat apps without a terminal, and everything still goes through bb, with its token, its `--project` and `--repo` scope and its audit trail. Your client never talks to Bitbucket itself.

   * For administrators: `--tools` and `--exclude` decide which of these are offered, as they decide the tools. The audit trail records reads, the resource list and prompts as `mcp_resource_read`, `mcp_resource_list` and `mcp_prompt_get`, with `resource` or `prompt` in place of `tool`; completions are not recorded. A SIEM rule that expects every record to name a tool needs to allow for them:

     ```json
     {"timestamp":"2026-08-29T09:32:40Z","event":"mcp_resource_read","resource":"bitbucket://projects/PAYMENTS/repos/ledger/pull-requests/42/diff","project":"PAYMENTS","repo":"ledger","status":"success","duration_ms":61,"user_identity":"alice","host":"https://bitbucket.example.com","scope":"PAYMENTS"}
     ```

7. **Administrators decide whether bb, or its MCP server, may be used at all ([ADR-100](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/100-administrators-can-switch-bb-off-or-make-it-read-only/), [#690](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/690)):**

   Three new system policy settings, which no flag, environment variable or user configuration overrides:

   | Setting | Registry value | Effect |
   |---|---|---|
   | `disable_mcp_server` | `DisableMCPServer` | `bb ai mcp serve` is refused; the rest of bb keeps working. |
   | `read_only` | `ReadOnly` | Commands that change Bitbucket are refused, `bb api` sends only `GET` and `HEAD`, and the MCP server offers only the tools that read. |
   | `disable_bb` | `DisableBB` | Every command is refused except help, `--describe`, `--version`, `bb doctor` and the completion scripts. |

   Set them in `/etc/bb/config.yaml`, or `%ProgramData%\bb\config.yaml` on Windows:

   ```yaml
   policy:
     read_only: true
   ```

   Or through Group Policy, as the registry value set to `1` under `HKLM\Software\Policies\bb`.

8. **See a pull request, a list or a diff as a view in your MCP client ([ADR-101](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/101-mcp-server-adopts-mcp-apps/), [#686](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/686)):**

   In clients that render MCP Apps, such as Claude Desktop, VS Code and Goose, the AI can now put what it found in front of you instead of describing it: a pull request with its reviewers' avatars and decisions, its builds and the ones its target branch requires, open tasks, its formatted description and its activity, comments included; a list of pull requests; or its diff, a file at a time, highlighted, with each comment on its line. It looks and reads like Bitbucket, and anything you click opens there.

   Ask for PAYMENTS/ledger#42 and the answer comes with its card; open the card for the full overview and its activity, or its diff. In the diff, select lines to add them to the chat, to ask about them or to comment on them; reply to a comment, and approve or request changes, without leaving the conversation. Ask the AI to open a pull request and it opens it; when you want a say in its description or reviewers first, it hands you its draft as a form to finish and submit, with the default reviewers and code owners filled in as Bitbucket's create page does. A view carries what it shows, so it still renders when you come back to the conversation, even without bb running, and it says when it was read. While it is on screen it keeps itself current: watch a build finish or a comment arrive without asking again, and the AI is told what changed. Terminal agents such as Claude Code show the usual text.

   * For administrators: a view has no network access; bb fetches the avatars with its own credentials and puts them in the result. `--exclude show` turns views off. A view keeps current by calling `refresh_view`, and the form suggests values through `suggest_form_values`: read-only tools only views are offered, each call recorded in the audit log like any other; `--exclude refresh_view` keeps views as they were drawn. What you do in a view goes through the AI's own tools, with their confirmations, and a view has no connection of its own to Bitbucket. The server tells agents to show views only to a person who is there, never in unattended work. Of Svelte, ERB, PHTML, Go HTML and Jinja templates only the markup is highlighted; `--highlight-templates` highlights the code in them too, with lexers a crafted file can keep busy for seconds, though no view waits for them.

9. **`bb api` authenticates like every other command ([ADR-083](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/083-no-flag-carries-a-secret/), [#707](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/707)):**
   * `-H` with an `Authorization`, `Proxy-Authorization` or `Cookie` header exits `2`, and so does a user or password in the endpoint URL or `--host`. A secret on the command line is readable in the process list and lands in shell history.
   * A script that passed its token that way stores it once with `bb auth login https://bitbucket.example.com --token-stdin`, or sets `BITBUCKET_TOKEN` in the environment.

10. **`bb pr create` needs no flags in a checkout, and `bb pr merge` takes a strategy ([ADR-102](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/102-a-value-read-from-where-a-command-runs-may-stand-in-for-its-flag/), [#705](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/705)):**

    Standing on a pushed branch, `bb pr create` is enough. The source is the branch that is checked out, the target is the repository's default branch, and the title is the commit's subject when the branch holds exactly one commit. At a terminal each is offered for you to accept or change. With nobody to ask they are used as they are and named on stderr, and a branch that holds several commits still needs `--title`. It prints the pull request's link, which every reported pull request now carries as `url`.

    ```bash
    git push -u origin feature/refunds
    bb pr create
    bb pr merge 42 --strategy squash
    ```

    `--strategy` takes any strategy the repository enables, and its default applies without it. `--dry-run` says so first when the repository has not enabled the one asked for.

11. **`bb search prs` takes a period, so it can answer "what did I work on" ([#697](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/697)):**

    What it lists has not changed. Without `--repo` that is every pull request you are involved in across every repository, whether you wrote it, are a reviewer on it or took part in it, and `--role` picks one of the three. What is new is the period: `--since` and `--until` bound the listing on the created, updated or closed date that `--date-field` names, and `--group-by week` or `repo` arranges the text output. With `--since` the listing holds the whole period rather than the first 25.

    ```bash
    bb search prs --role author --state all --since 2026-07-20 --until 2026-09-27 --group-by week
    ```

    * `--state` takes `merged` and `declined`, in `bb pr list` too, and `all` and `closed` no longer fail across repositories.
    * A pull request reports `closedDate` once it is merged or declined, and the issue keys its title and source branch mention:

### Other fixes worth knowing

* **An `https://` URL for a server that speaks plain HTTP is `permanent` (exit `1`) ([#704](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/704)).** It was `transient` (exit `10`) and tried three times, though the answer cannot change. The message says to check whether the URL should begin with `http://`.
* **An HTML error page is reported by its title ([#704](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/704)).** The message used to show the page's first 300 characters, which were all markup. Now it says what the page is:

  ```text
  validation: bitbucket API returned 400: an HTML page titled "Bad request - Bitbucket" (18389 characters; pass --full-error-body to see all of it)
  ```

* **Requests name bb ([#702](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/702)).** Every request carries `User-Agent: bb/<version> (<os>/<arch>)`, ending in `mcp` when the MCP server sends it, so an administrator can find bb's traffic, and an agent's, in Bitbucket's access log or at a proxy.
* **`bb branch list --details` prints the details.** It lists what Bitbucket's branch page shows beside each branch: how far it is ahead of and behind the default branch, its last commit, its builds and its pull requests. `--base` measures against another branch, tag or commit, and asks for the details by itself. Both flags used to be accepted and change nothing.

  ```text
  $ bb branch list --repo PAY/ledger --details
  feature/refunds  refs/heads/feature/refunds  6b9cb2216ad56a58f976325627a2d87ad41d6a2a  default=false  ahead=2 behind=1  2026-09-28 alice  pr=#42 OPEN  builds=1 successful, 1 failed
  master           refs/heads/master           0d4e1c7a9b3f52e86a1d7c40b9e2f35a6c8d1e07  default=true                     2026-09-27 bob
  ```

  Under `--json` each branch gains `ahead`, `behind`, `lastCommit`, `builds` and `pullRequests`, each left out when Bitbucket has nothing to report: the base has no counts, and a branch nobody built has no `builds`. Bitbucket names the pull request when a branch has exactly one, as `only`, and gives the counts alone when it has more:

  ```json
  {
    "data": {

      "branches": [
        {
          "id": "refs/heads/feature/refunds",
          "displayId": "feature/refunds",
          "latestCommit": "6b9cb2216ad56a58f976325627a2d87ad41d6a2a",
          "default": false,
          "ahead": 2,
          "behind": 1,
          "lastCommit": {
            "id": "6b9cb2216ad56a58f976325627a2d87ad41d6a2a",
            "displayId": "6b9cb2216ad",
            "message": "PAY-12: retry a declined refund",
            "author": { "name": "alice", "emailAddress": "alice@example.com" },
            "authorTimestamp": 1790586000000,
  ```

### Deprecation

* **`bb update --json`: `scheduled`, `staged`, `paths.staged` and `paths.swapResult` are deprecated and are removed in v6.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/), [ADR-092](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/092-bb-update-installs-the-new-binary-itself-before-it-exits/)).**
  * `bb update` installs the new binary itself before it exits, on every operating system, so these fields are always false or empty. Read `applied` instead.
* **`bb ai mcp serve --yolo` and `--allow-writes`, `bb ai mcp tools --safe-only`, and the `safe` and `exposure` fields of `bb ai mcp tools --json` are deprecated and are removed in v6.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/), [ADR-098](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/098-mcp-tools-that-decide-a-merge-ask-the-person/)).**
  * Every tool is exposed without `--yolo`, so the flags do nothing, `--safe-only` lists every tool, `safe` is always true and `exposure` always `SAFE`. Pass `--read-only` for a server that only reads, and read `asks` and `writes` instead of the fields.
* **`--matcher-display` on `bb branch restriction create` and `update` and on `bb project branch-restriction create` and `update`, and `--include-unique` on `bb build status stats`, `get` and `set`, are deprecated and are removed in v6.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/)).**
  * Neither ever changed a result. Bitbucket works out a matcher's display name from the matcher and ignores the one it is sent, and bb printed the same build counts with `--include-unique` and without it. Both are still accepted and print a warning on stderr; remove them from scripts. `bb build status get` lists each build with its state.
