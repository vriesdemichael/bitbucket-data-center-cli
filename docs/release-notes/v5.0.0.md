bb v5.0.0 works with every Bitbucket Data Center release Atlassian supports, completes what you type from your own Bitbucket, and makes its MCP server something you work with: it asks you before it merges, takes the pull request or file you hand it, and shows what it found as a view in your client.

It is a major release. Seven changes can break a script, a pipeline or an MCP configuration. They are under "Before you upgrade", each with what to change, and are the part to read first if bb runs in CI, in scripts or under an AI agent. What is deprecated keeps working until v6.0.0 and is listed at the end.

### New at the command line

* **Every Bitbucket Data Center release Atlassian supports ([ADR-088](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/088-every-bitbucket-release-atlassian-supports-is-served/), [#307](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/307)):**

  bb was built against the newest Bitbucket release and tested against that one alone. It now works with every release Atlassian supports, each tested against a real instance of it, and a release keeps working after Atlassian's support for it ends.

  An older release behaves like the newest except where it lacks something a later one added. There bb answers as the newest release would where it can, and otherwise refuses before it sends anything, naming the release that can do it:

  ```text
  $ bb branch restriction create --repo PROJ/app --type no-creates --matcher-id refs/heads/main
  unsupported: a no-creates branch restriction is not supported by this Bitbucket version (9.2.1); it needs 9.4.0 or later
  ```

  Before, Bitbucket accepted such a request and dropped the part it did not know, so a required build meant to spare pull requests blocked every one of them. `unsupported`, exit `14`, is a new error kind: a script that lists the kinds or exit codes it handles gains one. [Bitbucket Versions](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/reference/bitbucket-versions/) lists the four places where a release differs.

* **Tab completion that knows your Bitbucket ([ADR-089](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/089-completion-is-declared-by-the-argument-name/), [#407](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/407), [#397](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/397)):**

  Press tab after `bb pr merge ` and bb lists the open pull requests of the repository you are in, by number and title. After `bb branch delete ` it lists the branches, each with its latest commit message. Projects, repositories, tags, reviewers, file paths and the values a flag accepts complete the same way, read from your Bitbucket with your own credentials, in bash, zsh, fish and PowerShell.

  Homebrew and the `.deb` and `.rpm` packages set it up for bash, zsh and fish when they install bb, and Scoop sets it up for PowerShell, along with the agent skill. Anywhere else one command does it, and `bb doctor` says whether it is in place:

  ```bash
  bb completion install
  ```

* **`bb pr create` needs no flags in a checkout, and `bb pr merge` takes a strategy ([ADR-102](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/102-a-value-read-from-where-a-command-runs-may-stand-in-for-its-flag/), [#705](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/705)):**

  Standing on a pushed branch, `bb pr create` is enough. The source is the branch that is checked out, the target is the repository's default branch, and the title is the commit's subject when the branch holds exactly one commit. At a terminal each is offered for you to accept or change. With nobody to ask they are used as they are and named on stderr, and a branch that holds several commits still needs `--title`. It prints the pull request's link, which every reported pull request now carries as `url`.

  ```bash
  git push -u origin feature/refunds
  bb pr create
  bb pr merge 42 --strategy squash
  ```

  `--strategy` takes any strategy the repository enables, and its default applies without it. `--dry-run` says so first when the repository has not enabled the one asked for.

* **`bb search prs` takes a period, so it can answer "what did I work on" ([#697](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/697)):**

  What it lists has not changed. Without `--repo` that is every pull request you are involved in across every repository, whether you wrote it, are a reviewer on it or took part in it, and `--role` picks one of the three. What is new is the period: `--since` and `--until` bound the listing on the created, updated or closed date that `--date-field` names, and `--group-by week` or `repo` arranges the text output. With `--since` the listing holds the whole period rather than the first 25.

  The help of every command ends with examples to copy, showing the values a flag's description leaves you to guess. ### New in the MCP server

The server also asks you before a tool merges, or decides what merges. That changes an existing setup, so it is under "Before you upgrade".

* **Put a pull request, a diff or a file in front of the AI yourself ([ADR-099](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/099-mcp-resources-prompts-and-completions/), [#685](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/685)):**

  Until now the AI only saw what it went and fetched through bb's tools, so you had to hope it found the right pull request or file. Now you can hand it Bitbucket content yourself, the way you attach a file to a message: the pull request you are reviewing, its diff or its open comments, a file on any branch, tag or commit, or a single commit. Your MCP client helps you find it, suggesting projects, repositories, pull requests, paths and branches as you type, and it lists your own open pull requests and the ones waiting on your review, so the one you want is usually a click away.

  In VS Code, for example, choose Add Context > MCP Resources, pick the diff of pull request 42 in PAYMENTS/ledger, and ask what could break. Or type `/bitbucket.review_pull_request` to attach a pull request with its diff and open comments and ask for a review in one step. It works the same in any MCP client, including chat apps without a terminal, and everything still goes through bb, with its token, its `--project` and `--repo` scope and its audit trail. Your client never talks to Bitbucket itself.

* **See a pull request, a list or a diff as a view in your MCP client ([ADR-101](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/101-mcp-server-adopts-mcp-apps/), [#686](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/686)):**

  In clients that render MCP Apps, such as Claude Desktop, VS Code and Goose, the AI can now put what it found in front of you instead of describing it: a pull request with its reviewers' avatars and decisions, its builds and the ones its target branch requires, open tasks, its formatted description and its activity, comments included; a list of pull requests; or its diff, a file at a time, highlighted, with each comment on its line. It looks and reads like Bitbucket, and anything you click opens there.

  Ask for PAYMENTS/ledger#42 and the answer comes with its card; open the card for the full overview and its activity, or its diff. In the diff, select lines to add them to the chat, to ask about them or to comment on them; reply to a comment, and approve or request changes, without leaving the conversation. Ask the AI to open a pull request and it opens it; when you want a say in its description or reviewers first, it hands you its draft as a form to finish and submit, with the default reviewers and code owners filled in as Bitbucket's create page does. A view carries what it shows, so it still renders when you come back to the conversation, even without bb running, and it says when it was read. While it is on screen it keeps itself current: watch a build finish or a comment arrive without asking again, and the AI is told what changed. Terminal agents such as Claude Code show the usual text.

* **Files reach the AI in a format it can ingest ([ADR-094](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/094-mcp-tools-pass-content-to-the-model-in-a-format-it-can-ingest/)):**

  `get_file_content` passed every file as one string, whatever its size, and a file that is not text as unreadable characters. It now converts the file on the server: text as a window of numbered lines, so a long file is read a part at a time; an image as an image; a Word, PowerPoint or Excel file as its text; an archive as a list of its entries. Anything else is described by its type and size, with its page in Bitbucket. This is the MCP server's tool; `bb repo cat` still prints a file as it is.

### For administrators

* **Administrators decide whether bb, or its MCP server, may be used at all ([ADR-100](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/100-administrators-can-switch-bb-off-or-make-it-read-only/), [#690](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/690)):**

  Three new system policy settings, which no flag, environment variable or user configuration overrides:

  | Setting | Registry value | Effect |
  |---|---|---|
  | `disable_mcp_server` | `DisableMCPServer` | `bb ai mcp serve` is refused; the rest of bb keeps working. |
  | `read_only` | `ReadOnly` | Commands that change Bitbucket are refused, `bb api` sends only `GET` and `HEAD`, and the MCP server offers only the tools that read. |
  | `disable_bb` | `DisableBB` | Every command is refused except help, `--describe`, `--version`, `bb doctor` and the completion scripts. |

  Set them in `/etc/bb/config.yaml`, or `%ProgramData%\bb\config.yaml` on Windows:

  ```yaml
  policy:
    read_only: true
  ```

  Or through Group Policy, as the registry value set to `1` under `HKLM\Software\Policies\bb`.

* **Running and auditing the MCP server ([ADR-098](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/098-mcp-tools-that-decide-a-merge-ask-the-person/), [ADR-099](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/099-mcp-resources-prompts-and-completions/), [ADR-101](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/101-mcp-server-adopts-mcp-apps/)):**
  * A tool that asks records the answer: the audit record has `confirmation` (`accepted`, `declined`, `cancelled` or `unavailable`), and a call the confirmation stops is `status: denied`. The question is a record of its own, `status: asked`, written before the person answers, so an agent that asks and never answers still leaves a trace.
  * The audit trail redacts credentials wherever they appear in an argument or a resource URI ([#731](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/731)). An argument was redacted only when its name marked it secret or its whole value was a URL, and the `resource` field not at all, so a credential inside a path, a ref or a title was written to the audit file. Both now get the redaction `error_message` gets, which also catches `token=...` as Bitbucket quotes it back and `BITBUCKET_TOKEN=...`. A redacted URL reads `[REDACTED]` rather than `%5BREDACTED%5D`.
  * `--tools` and `--exclude` decide which resources and prompts are offered, as they decide the tools. The audit trail records reads, the resource list and prompts as `mcp_resource_read`, `mcp_resource_list` and `mcp_prompt_get`, with `resource` or `prompt` in place of `tool`; completions are not recorded. A SIEM rule that expects every record to name a tool needs to allow for them:

    ```json
    {"timestamp":"2026-08-29T09:32:40Z","event":"mcp_resource_read","resource":"bitbucket://projects/PAYMENTS/repos/ledger/pull-requests/42/diff","project":"PAYMENTS","repo":"ledger","status":"success","duration_ms":61,"user_identity":"alice","host":"https://bitbucket.example.com","scope":"PAYMENTS"}
    ```

  * A view has no network access; bb fetches the avatars with its own credentials and puts them in the result. `--exclude show` turns views off. A view keeps current by calling `refresh_view`, and the form suggests values through `suggest_form_values`: read-only tools only views are offered, each call recorded in the audit log like any other; `--exclude refresh_view` keeps views as they were drawn. What you do in a view goes through the AI's own tools, with their confirmations, and a view has no connection of its own to Bitbucket. The server tells agents to show views only to a person who is there, never in unattended work. Of Svelte, ERB, PHTML, Go HTML and Jinja templates only the markup is highlighted; `--highlight-templates` highlights the code in them too, with lexers a crafted file can keep busy for seconds, though no view waits for them.
  * For MCP clients: every tool declares all four MCP hints and a title as the specification defines them, so a client that decides its own prompts from the hints may prompt for different tools. `openWorldHint` is false on every tool, and `update_pull_request` and `disable_auto_merge` are destructive. `bb ai mcp tools` has `asks` (`always`, `never` or `when-setting-draft`) and takes `--read-only`. `bb ai mcp tools --json` for one tool:

    ```json
    {
      "name": "merge_pull_request",
      "description": "Merge a pull request. All required build checks must pass and all reviewers must have approved. Asks the person to confirm in the client before it runs.",
      "writes": true,
      "asks": "always",
      "safe": true,
      "exposure": "SAFE"
    }
    ```

* **`bb update` on premises ([ADR-092](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/092-bb-update-installs-the-new-binary-itself-before-it-exits/), [#637](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/637), [#633](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/633)):**

  `bb update` installs the new binary itself before it exits, on every operating system. On Windows it used to leave the swap to a PowerShell helper that ran after bb had exited. Application control such as AppLocker or WDAC blocked the helper, and bb had already reported success.

  Behind a release mirror, every download now goes through the mirror, with the CA and the client certificate it was configured with, and a mirror whose certificate this host does not trust is reported as a failure to fix, no longer as one to retry. `bb update --dry-run` verifies the release the mirror serves, its signature, its checksums and the archive itself, also when nothing newer is there. That makes it the check to run on a host after a rollout. A slow link no longer fails the download at the request timeout.

* **Requests name bb ([#702](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/702)).** Every request carries `User-Agent: bb/<version> (<os>/<arch>)`, ending in `mcp` when the MCP server sends it, so an administrator can find bb's traffic, and an agent's, in Bitbucket's access log or at a proxy.

### Before you upgrade

If you consume `bb` inside CI/CD pipelines, shell scripts, or AI agent toolchains, review this checklist before upgrading:

1. **`bb pr checks` gates on CI the way `gh pr checks` does ([ADR-091](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/091-a-command-may-report-the-state-it-read-through-its-exit-status/), [#646](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/646)):**
   * Without `--json`, `bb pr checks` and `bb pr build status` exit `1` when a build failed, and `8` when none failed and one is still in progress or has no result. They used to exit `0` whatever the builds said, so a gate written for `gh`, `bb pr checks 42 || exit 1`, let every pull request through.
   * A failed build wins over one still running, and a cancelled build counts as neither. The exit status covers every build, not only the `--limit` shown. When it is not `0`, a line on stderr says how many builds failed or are still running.
   * Exit `8` is new to `bb`. It is not an error kind, and only these two commands use it.
   * Under `--json` both commands still exit `0`, with each build's state in `data.statuses`, as `gh pr checks --json` does.
   * A script that runs either command for its output and relies on exit `0` adds `|| true`, or passes `--json`.
2. **`bb bulk` is gone, as the v4.1.0 notes announced ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/), [#608](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/608)):**
   * `bb bulk plan`, `bb bulk apply` and `bb bulk status` no longer exist, nor do `BB_BULK_STATUS_DIR` and the bulk policy, plan and apply-status schemas.
   * Set permissions, webhooks, default tasks and branch restrictions once on the project, with `bb project permissions`, `bb project webhook`, `bb project default-task` and `bb project branch-restriction`. Bitbucket applies them to every repository in the project.
   * For a setting Bitbucket keeps per repository, loop over `bb repo list --project PROJ --json` and run the `bb repo settings` command for each, previewing with `--dry-run`. The loop is safe to run again: a webhook create that finds its webhook already there reports it rather than adding a second.
   * The bb-bulk agent skill is gone too, so `bb ai skill install bulk` exits `2`. Delete any copy an earlier bb installed, in `.agents/skills/bb-bulk` or `.claude/skills/bb-bulk`, in a project or in your home directory. `bb doctor` names every copy it finds.
3. **`--dry-run` answers with a verdict, in its own member ([ADR-096](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/096-the-flags-choose-the-member-and-dry-run-answers-with-a-verdict/), [#616](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/616)):**
   * Under `--json`, a dry run answers in `preview` rather than `data`: a `tier`, one effect per change with its `action`, `target`, `outcome` (`would-apply`, `no-op` or `would-fail`) and `reasons`, and the `error` the real run would fail with. `dryRun`, `planningMode`, `capability`, `summary`, and per item `intent`, `predictedAction`, `supported`, `confidence`, `requiredState` and `blockingReasons` are gone; a script reading `summary` reads `effects` instead. `bb --json pr merge 42 --dry-run`, for a pull request that is already merged:

     <!-- docs-lint: envelope-shape -->
     ```json
     {
       "preview": {
         "tier": "preconditions-checked",
         "effects": [
           {
             "action": "update",
             "target": { "id": "42", "repository": "PROJ/app" },
             "outcome": "would-fail",
             "reasons": ["pull request is already merged"]
           }
         ],
         "error": { "kind": "conflict", "message": "pull request is already merged", "exitCode": 5 }
       },
       "meta": { "command": "pr merge", "bbVersion": "..." }
     }
     ```
   * A command that only reads still runs, and its data is in `preview.data`. A failure the check runs into, such as invalid arguments or a missing pull request, is `preview.error` rather than a top-level `error`, which under `--dry-run` now means only that no verdict was reached: `10` Bitbucket did not answer, `12` interrupted, `1` a bug in bb.
   * Without `--json`, a dry run that finds the run would fail exits with the code the real run would, so `bb pr merge 42 --dry-run && bb pr merge 42` stops at the check. It used to exit `0`. Under `--json` or `--yaml` a verdict exits `0`, with the verdict in the document.
   * The text output names each change and why it would or would not go through, in place of the `intent=... action=...` lines.
   * `bb ai mcp serve` no longer takes `--dry-run`.
   * There is no warning period: one document cannot carry the old preview beside the new one.
4. **`--describe` describes the whole document, for a run and for a dry run ([ADR-097](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/097-describe-describes-a-commands-output-in-every-mode/), [#616](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/616)):**
   * Under `--json` it answers in `description` rather than `data`. `run.outputSchema` is the JSON Schema of the whole document a run writes, meta and the error included, and `dryRun.outputSchema` the one `--dry-run` writes, beside `dryRun.behaviour` and `dryRun.tier`. `described` is gone, `command` is `meta.command` and `reason` is `run.reason`. A script reading `schema` reads `run.outputSchema.oneOf[0].properties.data`, or better, validates the whole document against `run.outputSchema`.
   * Without `--json` or `--yaml` it prints an outline of the fields for people, rather than the JSON Schema.
   * `bb <group> --describe` and `bb --describe` list their commands with what `--dry-run` does for each, rather than saying a group has nothing to describe. A path that names no command answers with `description.error`, exiting `0` under `--json`.
   * There is no warning period: one document cannot carry the old description beside the new one.
5. **The MCP server asks your permission in your MCP client, and offers every tool by default ([ADR-098](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/098-mcp-tools-that-decide-a-merge-ask-the-person/), [#620](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/620)):**
   * `bb ai mcp serve` moves to MCP's newer way of asking for permission, elicitation: the server asks, and your MCP client shows you the question. By default it offers every tool, as it did with `--yolo`, but a tool that merges, or decides what merges or gets released, asks you first. That covers merging, turning auto-merge on or off, approving or requesting changes, reporting a build status, creating a tag, and moving a pull request into or out of draft. Your client shows what the call will do, and it runs only once you accept. Before, the server hid most of these unless it started with `--yolo`, and then nobody was asked.
   * Locking the server down is now opt-in: with `--read-only` it offers only the tools that read. `--yolo` and `--allow-writes` do nothing, and warn.
   * You accept the pull request you were shown. If someone pushes to it before you accept, the merge or auto-merge is refused.
   * Those tools need a client that supports elicitation. One that does not gets error `-32021` for them, and nothing changes in Bitbucket.
   * What changes in the audit record, in the hints a client reads and in `bb ai mcp tools` is under "For administrators".
6. **`bb api` authenticates like every other command ([ADR-083](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/083-no-flag-carries-a-secret/), [#707](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/707)):**
   * `-H` with an `Authorization`, `Proxy-Authorization` or `Cookie` header exits `2`, and so does a user or password in the endpoint URL or `--host`. A secret on the command line is readable in the process list and lands in shell history.
   * A script that passed its token that way stores it once with `bb auth login https://bitbucket.example.com --token-stdin`, or sets `BITBUCKET_TOKEN` in the environment.
7. **A stored credential goes only to the host it was stored for ([#730](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/730)):**
   * A credential `bb auth login` stored for one Bitbucket is sent to that host alone. A command pointed at another host, by `--host`, `BITBUCKET_URL`, a `.env`, a workspace `.bb/config.yaml` or a full URL given to `bb api`, sends that host no credential unless one is stored for it too, and Bitbucket answers `401` for anything that is not public. The same holds for the fork lookup after `bb repo clone` of another host's URL, which also no longer shows that host your default host's client certificate. An alias of the stored host still counts as the same host.
   * A host profile in a workspace `.bb/config.yaml` gives that host its `url` and `username`, and nothing that acts as you: it never makes bb send a stored token or password, and its `client_cert` and `client_key` are ignored. A profile keyed to another host with its `url` set to your Bitbucket, or one naming another host as an alias of yours, was handed your token. If a workspace file set a client certificate, set it with `--client-cert` and `--client-key` on `bb auth login`, or in `BB_CLIENT_CERT` and `BB_CLIENT_KEY`.
   * A credential stored for `https://` is not sent to the same host over `http://`, so a `.env` or `.bb/config.yaml` naming your Bitbucket over `http://` can no longer send your token in the clear, and `bb clone` no longer passes it to git for an `http://` clone link. A login stored for `http://` still answers over `https://`.
   * Before v4.1.0 a host with nothing stored for it got the default host's credential, which sent your token to whatever host a cloned repository's `.env` or workspace file named. v4.1.0 closed that everywhere but `bb api` and the clone's fork lookup, without saying so in its notes; v5.0.0 closes those two.
   * A script that relied on the old fallback logs in to each host it talks to, `bb auth login <host>`, or sets `BITBUCKET_TOKEN` for the run.
8. **A credential goes into the configuration file in plaintext only when you ask ([ADR-047](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/047-credential-input-and-keyring-enforcement/)):**
   * Where the OS keyring cannot hold the secret, on a headless server, in most containers, or in WSL without `gnome-keyring`, `bb auth login` exits `1` and stores nothing. It used to write the secret into the configuration file in plaintext, with a warning on stderr, without being asked.
   * This affects a login on a machine with no keyring, including the token `bb repo clone` asks for when nothing is stored for the host. Where a keyring works, nothing changes.
   * To keep the old behaviour, pass `--allow-insecure-storage` to `bb auth login`. Better, in CI and containers, set `BITBUCKET_TOKEN` in the environment and do not log in at all. `BB_REQUIRE_KEYRING=1` and the `require_keyring` policy refuse plaintext even with the flag, and `--require-keyring` cannot be combined with it.
   * A credential already stored in plaintext keeps working, with its warning, so nobody is locked out by the upgrade. Only a new login needs the flag.

### Other fixes worth knowing
* **A project key or repository slug cannot carry a path.** A slug such as `repo/pull-requests/7/merge?version=3#` turned a request into one for another endpoint, so through the MCP server a tool that never asks could merge a pull request. A key or slug holding a slash, `?`, `#`, `%` or whitespace is refused.
* **A repository command no longer changes what its project defines ([#657](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/657)).** A repository's branch restrictions, default reviewer conditions and default tasks include the ones it inherits from its project. `bb branch restriction delete --repo`, given the id of an inherited one, deleted it from the project, and so from every repository in it. These commands now refuse an inherited entry and name the project command that changes it, and the listings mark what is inherited.
* **A branch restriction survives an update that is refused, and `--user` and `--access-key-id` work.** An update deleted the old restriction before it created the new one, so a refusal, for a user name that does not exist for instance, left the branch unprotected. The two flags had failed on every call.
* **A long transfer is no longer cut off.** `bb clone` was stopped after 60 seconds whatever it was doing, and `bb repo archive`, `bb repo cat` and the download in `bb update` had to finish within `request_timeout`. Each now runs for as long as it makes progress, and a failed `bb repo archive` leaves no partial file.
* **`bb ai skill install` reaches Claude Code.** It wrote the skill to `.agents/skills`, which Claude Code does not read. It writes `.claude/skills` as well now, and `bb ai skill remove` takes out both.
* **Git authenticates as the login `bb auth setup-git` set up ([#733](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/733)).** The helper line named bb and nothing else, so git pushed as whichever configuration file `BB_CONFIG_PATH` named when git ran, and two logins for one host could not be kept apart. The line now names the configuration file setup-git read, and `bb auth git-credential` takes it as `--config`. Run `bb auth setup-git` again to pin an existing setup; it replaces bb's own earlier line without `--force`.
* **`bb pr checkout` keeps the credential off git's command line**, where any local account could read it while git ran, as `bb clone` already did.
* **`--project` inside a clone means the project ([#725](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/725)).** In a clone, bb filled in the clone's repository beside `--project`, so `bb reviewer-group` and `bb repo ssh-key` refused it for naming both, and `bb reviewer condition` acted on the repository instead: `create --project` wrote the condition there. `bb search prs --role` was refused the same way. A scope you name now keeps the clone out of it. `bb reviewer condition` refuses `--project` and `--repo` together, as `bb reviewer-group` does.
* **`bb build required delete --dry-run` finds the check wherever it is ([#728](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/728)).** The preview looked for the check among the first `--limit` checks only, 25 by default, and predicted `no-op`, "not found", for one further down, which the real run then deleted. It reads every check now.
* **An `https://` URL for a server that speaks plain HTTP is `permanent` (exit `1`) ([#704](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/704)).** It was `transient` (exit `10`) and tried three times, though the answer cannot change. The message says to check whether the URL should begin with `http://`.
* **Creating a webhook that is already there reports it ([#729](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/729)).** Bitbucket stores a second webhook with the name, URL and settings of one it has, and both fire, so a setup script run twice made two. `bb webhook create`, `bb project webhook create` and `bb repo settings workflow webhooks create` now report the webhook that is there and exit `0`, with `created: false` under `--json`. One with the same name and URL and other settings is refused as a `conflict` (exit `5`) that names it and what differs; change it with `update`. `--dry-run` predicts both. Bitbucket never returns a webhook's endpoint password, so a password you pass is not compared, and a note on stderr says so.

* **An HTML error page is reported by its title ([#704](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/704)).** The message used to show the page's first 300 characters, which were all markup. Now it says what the page is:

* **Output that was wrong, for a script that reads it:**
  * `bb pr get` lists a pull request's reviewers. It listed everyone who took part, so whoever merged it or commented in passing appeared as a reviewer, and the review summary counted a real approval as missing.
  * A resolved comment thread counts as resolved, in `bb pr comment list` and in the unresolved count of a pull request.
  * `bb branch list` marks the default branch ([#658](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/658)). Every branch read `default: false`.
  * `bb diff pr --name-only` prints each path as it is, no longer as `dst://path`, and names binary files. `bb diff refs --stat` counts the change the diff shows; it counted the reverse. `--path` on `bb diff commit` and `bb diff refs` prints a unified diff; it printed JSON.
  * `bb deployment get` reports the commit that was deployed as `toCommit`. `fromCommit` is the commit the previous deployment deployed, which is what Bitbucket means by it.
  * `bb api --json` carries a body that is not text as base64 and says so in `meta.encoding`. It used to replace every byte that was not valid text.

### Deprecation

* **`bb update --json`: `scheduled`, `staged`, `paths.staged` and `paths.swapResult` are deprecated and are removed in v6.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/), [ADR-092](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/092-bb-update-installs-the-new-binary-itself-before-it-exits/)).**
  * `bb update` installs the new binary itself before it exits, on every operating system, so these fields are always false or empty. Read `applied` instead.
* **`bb ai mcp serve --yolo` and `--allow-writes`, `bb ai mcp tools --safe-only`, and the `safe` and `exposure` fields of `bb ai mcp tools --json` are deprecated and are removed in v6.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/), [ADR-098](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/098-mcp-tools-that-decide-a-merge-ask-the-person/)).**
  * Every tool is exposed without `--yolo`, so the flags do nothing, `--safe-only` lists every tool, `safe` is always true and `exposure` always `SAFE`. Pass `--read-only` for a server that only reads, and read `asks` and `writes` instead of the fields.
* **`--matcher-display` on `bb branch restriction create` and `update` and on `bb project branch-restriction create` and `update`, and `--include-unique` on `bb build status stats`, `get` and `set`, are deprecated and are removed in v6.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/)).**
  * Neither ever changed a result. Bitbucket works out a matcher's display name from the matcher and ignores the one it is sent, and bb printed the same build counts with `--include-unique` and without it. Both are still accepted and print a warning on stderr; remove them from scripts. `bb build status get` lists each build with its state.
* **`--limit` and `--all` on `bb build required delete` are deprecated and are removed in v6.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/)).**
  * They bounded the checks the preview looked through, and it looks through all of them now. Both are still accepted and print a warning on stderr; remove them from scripts.
