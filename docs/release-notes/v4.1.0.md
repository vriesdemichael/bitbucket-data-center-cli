bb v4.1.0 adds `bb doctor` for configuration problems and closes most of the remaining gap with `gh` for pull requests and repositories. It also makes failures say what actually happened: whether a request that never got an answer may have been applied, whether a listing was cut short, and which file or policy refused a command.

It is a minor release with no breaking changes. Most of the behaviour that changes is a fix: v4.0.0's decision records and release notes already specified it, and this release makes the binary keep those decisions everywhere.

### Highlights

* **`bb doctor` ([ADR-086](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/086-bb-doctor-reports-the-configuration-without-loading-it/), [#597](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/597)):** Checks the stored, workspace and system configuration files and reports every problem at once:
  * schema violations, with their key and line;
  * keys a file never reads, such as `require_keyring` in a user's own file;
  * where each effective setting comes from;
  * whether a required OS keyring answers.

  It needs no Bitbucket host, makes no network call, and exits 1 when there is anything to fix.
* **Closer to `gh` ([ADR-050](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/050-shallow-aliases-for-deep-command-paths/), [#575](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/575)):**
  * `bb pr view`, `bb pr edit` and `bb pr close` resolve, and `bb pr checks` shows a pull request's build statuses.
  * `bb pr ready` marks a draft ready for review without asking for its version, and `--undo` turns it back into a draft ([#602](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/602)).
  * `bb repo get`, also spelled `bb repo view`, describes a repository and prints its README ([#605](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/605)).
* **An interrupted change is no longer reported as safe to retry ([ADR-011](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/011-error-taxonomy-and-cli-exit-contract/), [#574](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/574)):**
  * **The problem.** Suppose bb sends a change (a pull request, a comment, a merge, a delete) and the connection drops or times out before Bitbucket answers. Bitbucket may already have applied it. bb used to report that as `transient`, exit `10`, which is the code retry wrappers act on, so a retry could create the same pull request or comment twice.
  * **Now.** Such a failure is `unknown_outcome` and exits `13`, outside the retry range, and the message says to check whether the change landed before sending it again. A failure before the request left the machine is still `transient`, so retrying it stays safe.
* **Releases you can verify, and a self-update that stays on https unless you allow otherwise.** This matters if you check what you install or mirror releases internally; the steps are in [Release Verification](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/advanced/enterprise-hardening/#1-release-verification-pre-deployment).
  * **Per-archive SBOMs ([#584](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/584)).** Each release archive carries its own SBOM: the list of every module the binary inside it is built from, which vulnerability scanners and compliance reviews read.
    * It is generated from that binary, because each platform links different modules.
    * It is attested against the archive, so `gh attestation verify` proves the SBOM describes that archive.
    * It replaces the single `sbom.spdx.json`, which inventoried the build checkout rather than any binary.
  * **https for update mirrors ([ADR-059](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/059-enterprise-update-controls-and-release-mirrors/)).** `bb update` fetches release mirrors over `https`, because over plain HTTP anyone on the network path can read or hold back what the mirror serves.
    * A mirror without TLS needs `bb update --allow-http` or `BB_ALLOW_HTTP_UPDATE=1`.
    * `allow_http_update: false` in system policy refuses plain HTTP for every user.
  * **Pinned actions.** The workflow that builds and signs releases runs GitHub Actions pinned to exact commits, so a moved tag cannot change what builds the binary.
  * **Windows and macOS CI.** The unit suite runs natively on Windows and macOS as well as Linux.

### Fixes: v4.0.0 decisions the binary now keeps everywhere

1. **Every destructive delete confirms ([ADR-073](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/073-interactive-when-a-person-is-there-explicit-when-not/)).**
   * The rule: destructive commands confirm when a person is present and require `--yes` when not, and `--yes` is inert on a repository inferred from the git remote.
   * v4.0.0 enforced it for `bb repo delete` and `bb auth gpg-key clear`. Deleting a branch, a tag or a webhook now follows it too.
   * In a pipeline, pass `--yes` and name the repository with `--repo PROJECT/slug`.
2. **Invalid arguments exit `2`, as the v4.0.0 notes promised.** A subcommand that a command group does not know printed the group's help and exited `0`, which put prose on stdout under `--json`. It now exits `2` (`validation`), and the help goes to stderr.
3. **Error kinds match the taxonomy ([ADR-011](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/011-error-taxonomy-and-cli-exit-contract/), [#574](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/574)).**
   * A rejected TLS certificate or a DNS failure is `permanent` (exit `1`). It is not `transient` (exit `10`), which invites a retry that cannot succeed.
   * A `401` that refuses a known user is `authorization`, not `authentication`.
4. **A capped listing says it was capped ([ADR-074](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/074-a-service-takes-a-cap-never-a-page-size/), [#573](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/573)).** `--limit` has capped the total since v4.0.0. Every listing that takes it now also reports `meta.limitReached`, and MCP results and text output say so too.

### Other fixes worth knowing

* **Error messages no longer carry raw Bitbucket responses.**
  * An upstream response body is summarised, and credentials in it are redacted, before it reaches a message. Some bodies ran to 18 KB.
  * `error.details` carries `upstreamStatus` and, when Bitbucket names one, `upstreamException`.
  * `--full-error-body` prints the whole body when you need it.
* **`--dry-run` changes nothing on the local machine either.** `bb auth logout` and `bb auth setup-git` used to apply their change under `--dry-run`.
* **A configuration file bb cannot read is an error, not an empty file** ([#567](https://github.com/vriesdemichael/bitbucket-data-center-cli/issues/567)).
  * Commands name the file and stop, instead of reporting that you are not logged in.
  * `bb auth login` no longer rewrites a file it could not read, which removed every other host.
  * `BB_DISABLE_STORED_CONFIG=1` no longer reads the stored file at all.

### Deprecation

* **`bb bulk` is deprecated and is removed in v5.0.0 ([ADR-084](https://vriesdemichael.github.io/bitbucket-data-center-cli/latest/adr/084-a-removed-flag-warns-for-one-major/)).**
  * It warns once per invocation on stderr, so `--json` output stays clean.
  * Permissions, webhooks and default tasks set at project level already apply to every repository in the project. For anything else, loop over `bb repo list`.
